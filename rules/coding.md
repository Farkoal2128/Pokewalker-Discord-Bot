# Coding Rules

- Prefer small cohesive units and explicit boundaries.
- Keep domain rules separate from I/O and framework plumbing where practical.
- Preserve backwards compatibility unless an approved requirement says otherwise.
- Avoid speculative abstractions and unrelated cleanup.
- Make failure behavior explicit.
- Treat warnings, TODOs, and temporary bypasses as tracked work rather than invisible debt.
- Comments should explain why, constraints, or non-obvious tradeoffs—not restate the code.
- Public behavior requires documentation, contract coverage, or both.
