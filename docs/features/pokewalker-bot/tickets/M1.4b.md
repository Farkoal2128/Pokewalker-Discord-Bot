# M1.4b — ❗ reaction reconcile: desired/actual, crash-safe removal, startup sweep

**Tier:** seam (gateway side effects; persisted state). Dispatch after M1.4, before M1.5.

**Read:** README.md:19 (D3: ❗ on empty→non-empty; `/walker` removes it), :428
(removing the bot's own reaction needs no Manage Messages); research adaptation.md:99 (a
failed or missing reaction never deletes an encounter); discord-interactions.md:65 (commit
before Discord); PLAN §4.1 P16; M1.1 `reactions` (desired `add|remove`, actual `none|added`);
M1.4 `channel_policy`; review-5.md.

**Goal.** `pokewalker/services/reactions.py`: one idempotent coroutine
`reconcile_reaction(encounter_id)`, called **after commit** by M1.5 (add side) and M1.6
(remove side), never inside a writer transaction:

1. Read the row. If `desired='add'`, `actual='none'` and the channel policy has `react=1`:
   add the bot's own ❗ to `(channel_id, message_id)`, then compare-and-set `actual='added'`.
   Re-adding a present own reaction is a Discord no-op, so a crash between the API call and
   the DB write is repaired by the next reconcile.
2. Re-read `desired`. If it is `remove`: **always** attempt to delete the bot's own reaction,
   whatever `actual` says — an interrupted add leaves `actual` uncertain, and deleting an
   absent reaction is harmless (a 404 counts as removed) — then **retire the row (delete
   it)**. A crash between the Discord delete and the row delete leaves `desired='remove'`,
   which the next reconcile retries once (404) and then retires. Rows that exist are the only
   pending work, so `/walker` (M1.6) and the startup sweep never touch completed removals.
3. Other Discord failures (permission, rate limit, outage) leave the row for a later reconcile
   and never touch the encounter; permission errors log once per channel.
4. Startup sweep: after M1.2's `setup_hook`, run `reconcile_reaction` for every remaining row
   with `desired='remove'` or `desired='add', actual='none'` (all of them pending), so a crash
   mid-flight is repaired at restart without waiting for the next `/walker`.
5. Serialize per reaction: `reconcile_reaction` holds an in-process `asyncio.Lock` keyed by
   `encounter_id` for its whole run and re-reads the row after acquiring it; a retired or
   `remove` row skips the add. So an in-flight add cannot recreate the ❗ after retirement:
   it either runs first and is then removed, or finds no row and does nothing.
