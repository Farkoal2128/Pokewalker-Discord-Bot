**Goal.**

- Migration `000N_opt_outs.sql`: `opt_outs(guild_id, user_id, created_at, PRIMARY
  KEY(guild_id,user_id))`, kept across deletion; `marker_log_init(id INTEGER PRIMARY KEY
  CHECK(id=1), at REAL NOT NULL)` (used by M4.1c).
- `pokewalker/services/deletion.py`
  - `run_marker(writer, path, authorize, **fields)` queues **one job**: `await
    authorize(conn)` when given (refusal: no marker, no change), `append_marker`,
    `apply`. The job wraps its body in `except BaseException:` that, once the marker
    exists, calls `append_void` **before** re-raising, so the writer rolls back after
    the void. This covers compute errors and the writer's abort, which cancels the job
    at an await. The caller never writes a void: a cancelled caller leaves its job
    running to commit or void itself. A commit failure, or a cancellation landing in
    the writer's commit after the job returned, leaves the marker valid, like a crash
    between append and commit; replay applies it (deletion-safe, Round 11 ruling).
  - `apply(conn, state)`: `DELETE FROM profiles WHERE profile_id IN delete_ids`
    (cascade); `opted_out` True → `INSERT OR IGNORE opt_outs`, False → `DELETE`, None →
    untouched; each reset → `with_receipt(f"reset:{marker_id}", "reset", <insert
    mod_audit>, profile_id=None)`. Receipts only dedupe that audit; they never decide
    whether state applies.
  - `opted_out(conn, guild_id, user_id) -> bool` for M4.1's gates.
- `config.py` adds `POKEWALKER_MARKER_LOG` (default beside the DB, never inside it).
